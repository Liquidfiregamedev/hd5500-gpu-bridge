# HD5500 GPU Bridge: changelog, ideas and decisions

Running record per version. Newest first. "Status" is what was verified where: *emu* = my Wine/D3D11 harness (`smoke.c`, 6 modes), *laptop* = the user's Lenovo Z70-80 (HD 5500, Win10).

## v13.75 (2026-10-20) — uniform ring and descriptor fast path now reach Waylith's real per-draw pattern
**Measured v13.74 on the laptop (speed test 211523, heat guard + 45 fps cap, against v13.72 speed test 205537 on the same day):** bridge **2.3 ms per frame (was 3.3), 5.5 µs per draw (was 7.2)**. Index pool: works — D3D11 index-buffer calls 25,457 for the whole session (was ~1 per draw, millions), BindIndexBuffer 0.06 ms/frame (was 0.33), 2.5 million pool hits, 9,685 copies, 0 restarts. Upload merging: 466,000 uploads folded, UploadMemory 4.7 µs per call (was 10.5). Pictures: no problems reported. fps 37.3 average / 1% low 9.2 (was 34.8 / 9.0): still decided by the 22% throttle cycles after ~3 min and by the heat guard's 30 fps periods. **Two parts did not engage:** uniform ring windows=0, content fast path matches=5.
**Why (found in the decompiled engine, `Waylith.Rendering.VulkanMeshDrawEncoder.TryUploadUniforms` / `MeshBatchRenderer`):** Waylith does not use dynamic uniform offsets. Each draw's uniforms are written into a window of the 4 MB "DrawCallBuilder.Uniforms" buffer (usage UNIFORM only, host-visible) and that window's offset is written into a **new descriptor set as a plain uniform buffer** — which is also why every draw gets a new set. v13.74 only handled dynamic uniform buffers, and the content key included the uniform offset, which differs per draw.
1. **Uniform ring for plain uniform buffers** (`RW_GPU_UNIFORM_RING_STATIC=0` = dynamic ones only, as v13.74; `RW_GPU_UNIFORM_RING=0` = off). Same rules and fallbacks as v13.74 (pure constant buffer, host-visible with CPU shadow, never a transfer destination, window ≤ 64 KB, recordings without transfer writes), with bindUniformBuffer's own range rule.
2. **Content key without uniform offsets** (`RW_GPU_SET_CONTENT_UBO=0` = offsets in the key, as v13.74). Sets that differ only in their uniform-buffer offset now take the fast path: textures and samplers stay bound, the uniform buffers (and dynamic ones) are re-bound with their new offsets.
New harness check `ubowin` (suite now 34): the water pass from two new sets that differ only in the uniform offset (the second window tints the water red) — fast path + ring give exactly the old path's picture, the tint is visible, the fast path fired. Tests: 34/34 in default, submit-thread mode and with all switches set to old behaviour.
Expected: UploadMemory mostly gone (~0.3 ms) and BindDescriptorSet clearly lower (~0.2–0.4 ms) on top of v13.74. Watch: `[RW-GPU-UBRING] first batch`, `uniform ring: windows=` growing, `descriptor sets bound by content match=` growing.

## v13.74 (2026-10-20) — the two bigger rebuilds: uniform ring and index pool (includes everything from v13.73; prepared while the v13.72 test is pending)
**User request:** "Do the bigger rebuild, keep it switchable". Both structural ideas from the v13.73 research, each with its own switch back to v13.73 behaviour and its own harness check.
1. **Uniform ring** (`RW_GPU_UNIFORM_RING=0` = v13.73; `RW_GPU_UNIFORM_RING_MB` = size, default 4). Waylith binds a different 256-byte-aligned window of a large host-visible uniform buffer per draw; until now each window was copied into that buffer's own DEFAULT D3D11 buffer with `UpdateSubresource1` (6–12 µs each, ~90 per frame) and the upload commands were recorded per draw. Now the windows of a command buffer are captured at record time (their uploads are not recorded at all); at execution all of them are copied from the CPU shadow into ONE DYNAMIC constant buffer with ONE `Map(WRITE_NO_OVERWRITE)` (DISCARD only when the ring wraps) and each draw binds the ring at its window with `*SetConstantBuffers1`. This is the DXVK/NVIDIA/AMD "one big buffer, NO_OVERWRITE appends, constant-buffer offsets" pattern; the ring is bound directly (Dawn found a ring copied back into a DEFAULT buffer stalls on Intel). No fences needed: NO_OVERWRITE only appends after the last write, DISCARD gives fresh memory, and the immediate context is locked for the whole submit. Qualifies: dynamic uniform buffers whose D3D11 buffer is a pure constant buffer, in host-visible memory with a CPU shadow, never a copy/fill/update destination, window ≤ 64 KB, feature level 11_1 with NO_OVERWRITE for dynamic constant buffers. Recordings with buffer copies/fills/updates or secondary command buffers, a ring too small for the batch, or a failed Map: each window falls back to "upload, then bind the original buffer". Log: `[RW-GPU-UBRING] uniform ring … created`, `first batch: N uniform windows … copied with one Map`, and `uniform ring: windows= fallbacks= maps= wraps=` in the `[RW-GPU-IA]` line. Estimate: most of the 1.1 ms/frame UploadMemory time plus fewer recorded commands.
2. **Index pool** (`RW_GPU_INDEX_POOL=0` = v13.73; `RW_GPU_INDEX_POOL_MB` = size, default 16). Every map section has its own index buffer, so ~495 draws per frame each switched the D3D11 index buffer (~1.8 µs per `IASetIndexBuffer`, 0.9–1.0 ms/frame). The pool is one large DEFAULT index buffer: the first draw from an index buffer copies it into a pool slot on the GPU (`CopySubresourceRegion`); afterwards the draw binds the pool (usually already bound, so no call) and reaches its slot through firstIndex (v13.66 folding). A slot is re-copied whenever the bridge wrote the original since (new `ObjectMemory::contentVersion`, bumped by uploads, maps, buffer copies, update/fill, query results and image→buffer copies); GPU commands run in order, so a re-copy never changes what an earlier draw reads. vkCmdBindIndexBuffer now only records the binding; it is resolved at the next indexed draw, after that draw's uploads. Only plain index buffers (no UAV/stream-out, ≤ 1 MB). Pool full → starts over; 4 restarts within 10 s → switches itself off for the session (`[RW-GPU-IDXPOOL] … do not fit … switched off`). Indirect indexed draws keep the original buffer. Log: `[RW-GPU-IDXPOOL] index pool … created`, `first index buffer copied into the pool`, and `index pool: hits= copies= restarts=` in `[RW-GPU-IA]`; the existing `index-buffer binds: D3D11 calls=` counter should drop from ~1 per draw to a few per frame.
New harness checks (suite now 33): `ubring` (three windows per frame, new colours every frame: ring on, off, wrapping every frame, too small = fallback — all identical, newest colours) and `idxpool` (water pass drawn from a host-mapped and a copy-filled index buffer with wrong indices in frame 1: pool on, off, restarting until it switches off, too small — all identical to the normal water picture; the 1-frame picture differs, so stale indices would be caught).
Tests: suite 33/33 in default, submit-thread mode, all v13.73/v13.74 switches set to old behaviour, and with the D3D11 debug-layer variable set.
**Baseline before deploying (v13.72, map test 204653, 20 Oct 20:47, heat guard and 45 fps cap not ticked):** 56.9 fps average, 1% low 12.7 fps, frame p95 21 ms; bridge 4.1–4.5 ms per frame for ~460 draws (9.8 µs per draw). Per frame: DrawIndexed 1.3 ms (460×), BindDescriptorSet 0.9–1.0 ms (251×, content fast path not in v13.72: fast=16 vs full=3.1 million), UploadMemory 0.7–0.8 ms (86×, 8–10 µs), BindIndexBuffer 0.4–0.5 ms (356×), PushConstants 0.2 ms, BindPipeline 0.15 ms. CPU 72% of nominal on average, lowest 45%, no firmware limit and no 22% collapse in this run. The four big hitches (3.4 s, 2.5 s, 0.9 s, 1.0 s) coincide with the map test's frame dumps at frames 1800/3600/10532 (diagnostics only); the 50–100 ms cluster at 253–262 s is game-side (2 ticks per frame, map update 10–45 ms, bridge 0 slow buffers). v13.74 targets about 1.5–2 ms of the 4.5 ms.

## v13.73 (2026-10-20) — descriptor sets matched by content, merged uploads (prepared while the v13.72 test is pending)
**User request:** "Keep optimizing with possible fallback for the smallest increases. Look on the internet for more ideas". Every item below has its own switch back to v13.72 behaviour. Measured basis: speed test 150140 (v13.70, ~600 draws/frame): BindDescriptorSet 1.8–2.2 ms/frame (403 binds, 4.4–5.4 µs each), UploadMemory 1.1 ms/frame (89 uploads, 12.6 µs each while throttled).
1. **Descriptor-set fast path by content** (`RW_GPU_SET_CONTENT_FAST=0` = handle-only, as before). The v13.63 fast path (re-bind only the dynamic uniform buffers when the same set is bound again) never fired in RimWorld: the session counter showed `fast=0 full=4.6 million`, because Waylith allocates a new VkDescriptorSet for every draw. The set's content (exact list of textures, samplers, uniform buffers and binding shape) is now captured at record time and compared exactly (no hash) with the previous bind of that set index; equal content with nothing in between that could change bindings takes the fast path. Sets with storage images/buffers, input attachments, inline uniforms or swizzle-emulated views keep the full bind. New log line `[RW-GPU-SET] descriptor-set content fast path in use` (once) and the count in the `[RW-GPU-IA]` line. Gain depends on how often consecutive draws share textures; estimate 0.3–1.2 ms/frame. Note: this is the first time the v13.63 fast-path logic runs in the game at all — if textures look wrong, test with `RW_GPU_SET_CONTENT_FAST=0` first.
2. **Upload merging at record time** (`RW_GPU_UPLOAD_MERGE=0` = one upload per window). Waylith binds a different small window (a few hundred bytes) of the same large host-visible buffer per draw, and every window was its own `UpdateSubresource1` at execution. All host writes are finished before submit, so the earliest upload of a buffer now carries the nearby later windows (gaps up to 4 KB, clusters up to 256 KB); the existing per-execution dedupe (v13.24) skips the contained ones. Only for buffers the GPU cannot write (no UAV/stream-out/render-target binding) and only in recordings without copy/fill/update-buffer, query-result copies or secondary command buffers. Log line `[RW-GPU-UPLOAD] merging small buffer uploads per recording` (once) and the merged count in `[RW-GPU-IA]`. Research basis: DXVK/NVIDIA/AMD guidance ("UpdateSubresource sub-optimal for frequent small updates", "map a few times per frame"). Estimate 0.3–0.9 ms/frame.
3. **UAV declaration check cached** (`RW_GPU_UAV_CHECK_CACHE=0`): the diagnostic "shader declares uN but the slot is empty" check ran for every draw; it now runs once per (pipeline, resolved UAV list). Est. 0.02–0.05 ms/frame.
4. **Map tests: no mutex per draw in untraced frames** (`RW_HD5500_DIAG_HINTS=0`): with diagnostics on, every draw took the frame-diagnostics mutex twice even when the frame was not being traced. Map-test numbers move closer to normal play; no effect in normal play (diagnostics off).
**Second round (user: "Is that all? Try to find more both on HD5500, cache, disk and Windows level"):**
5. **Game process opts out of Windows power throttling** (`RW_GPU_HIGHQOS=0` = Windows' default). `SetProcessInformation(ProcessPowerThrottling)` with EXECUTION_SPEED control and state 0 = "never run this process on the efficient/slow schedule" (EcoQoS/LowQoS). Process-local, ends with the game. Log line `[RW-GPU-QOS]`. Benefit probably small (Windows rarely throttles a foreground game), free.
6. **PC check** (menu Laptop health, was "Power check"; read-only): adds graphics chips (some Z70-80 models also have a GeForce 840M, which has a real Vulkan driver — if this laptop has a working one, RimWorld could run without the bridge), model and BIOS, Lenovo power/thermal software and DPTF driver, firmware speed-limit events of the last 7 days (Windows event log, Kernel-Processor-Power 37), free space/bus/media of C: and the stick, TRIM, the three shader-cache sizes, page file, Defender status and exclusions, Game Bar recording, visual effects, Turbo setting, search indexer, and a numbered **Suggestions** list with the undo for each. Fixed: on this Dutch Windows the CPU-speed counter query failed ("Invalid query") — now falls back to the WMI clock.
7. **Two optional Windows tweaks with undo buttons** (Laptop health page; each asks for confirmation; `PC-Tweaks.ps1`, log in `reports\pc-tweaks-log.txt`): **Cool mode (Turbo off)** = a *copy* of the active power plan with maximum processor state 99% (no Turbo: 2.2 GHz instead of up to 2.7 GHz), activated; "Undo cool mode" re-activates the old plan and deletes the copy — an experiment against the 2-second 22% throttle cycles (less heat for ~12% less peak). **Game Bar recording off** (two HKCU values; undo restores the saved values). Defender exclusions are deliberately not a button (security setting): the PC check prints the exact add/remove command for the user to decide.
8. **.NET experiment allowed in experiment-env.txt:** `DOTNET_TieredPGO=0` (and `DOTNET_Tiered*`, `DOTNET_TC_*`): no background re-compilation of game code in the first minutes. GC tuning stays as is (GC was measured at 0.3–0.7% of frame time).
Research for this round (agent, sources in RESEARCH seventh pass): Game Bar background recording costs fps on slow PCs; Game Mode helps minimum fps on 2-core CPUs (keep on); HAGS and "optimizations for windowed games" are not available for HD 5500/Win10; Intel's "Maximum Performance" graphics power plan helps little when the CPU is the limit; Lenovo Energy Management's battery conservation mode lowers charging heat (battery here is at 68% health and was charging during runs); Kernel-Processor-Power event 37 shows firmware-ordered slowdowns.
New harness checks (suite now 31): `setcopy` (new set handle with identical content draws identically; a set with different textures in between is fully re-bound; a different set really changes the picture) and `multiwin` (three windows of one persistently mapped uniform buffer, new colours every frame: merged uploads give the same picture as one upload per window, with the newest colours).
Tests: suite 31/31 in default, submit-thread mode, and with all four new switches set to the old behaviour.
Research (seventh pass, see RESEARCH): DYNAMIC NO_OVERWRITE ring buffers instead of `UpdateSubresource1` and per-memory index/vertex buffers (one `IASetIndexBuffer` per memory block instead of one per map section: 495 index-buffer switches per frame at ~1.8 µs) are the two big remaining structural ideas; not started.

## v13.72 (2026-10-20) — texture binds without needless hazard checks; fewer hash lookups while recording
**User request:** "Keep optimizing code and find more optimizations". Targets from the last speed test (per frame, ~600 draws): descriptor-set binds 0.8 ms (textures dominate: `binds tex` in the profiler), recording-side upload tracking ~3 lookups per draw.
1. **SRV binds: state-cache check before the hazard check** (`RW_GPU_SRV_CACHE_FIRST=0` = old order). During a render pass every texture bind asked the hazard tracker, which costs three COM calls per view (GetResource, Release, GetDesc) — also when the same view was already bound in that slot (about half of all binds). Now an already-bound view is skipped first. Safe because the hazard tracker now has a version that changes whenever the written resources change (render targets, depth, UAVs), and the SRV cache is dropped when it does. Est. 0.1–0.3 ms/frame.
2. **Recording: "recently recorded" check before the upload hash** — per draw the same 2–3 buffers (vertex, instance, index) are recorded again; a 4-entry check now answers most of them without hashing, and the hash insert uses `try_emplace` (never allocates a node for an existing key). Est. 0.05–0.15 ms/frame.
Tests: suite 29/29 in default, submit-thread mode, and old order with the D3D11 debug layer.

## v13.71 (2026-10-20) — heat guard that actually engages, 45 fps cap in the menu, more small wins
**User request:** "Add these functions and keep optimizing" (heat guard + frame cap in the menu, after the speed test showed the laptop throttling in ~2 s cycles down to 22% clock).

**Heat / throttling:**
1. **Heat guard detection fixed.** The guard (Laptop health → "Heat guard: cap to 30 fps while the laptop throttles or runs hot", `RW_GPU_THERMAL_GUARD=1`) needed 3 throttled seconds *in a row*; this laptop throttles in ~2-second bursts (run 150140: 22% clock / 115% clock alternating every ~2 s), so it would never have engaged. Now a CPU clock below 50% also counts as throttled, and the guard engages when **3 of the last 10 seconds** were bad; it lifts after 20 normal seconds as before.
2. **Menu option "Frame-rate cap 45 fps (less heat, always on)"** (Laptop health page, `RW_GPU_FPS_CAP=45`). Game speed unaffected. Together with the heat guard: 45 fps normally, 30 fps while throttling.
3. **The cap now waits with a high-resolution waitable timer** (Windows 10 1803+) instead of Sleep(1) steps plus a SwitchToThread spin over the last 1.5 ms — the waiting costs no CPU (less heat, the point of the cap).

**Bridge (recording side):**
4. **Bound descriptor sets de-duplicated by layout** (`RW_GPU_BOUND_SET_DEDUPE=0` = old): a new set replaces an earlier bound set with the same layout. Waylith binds a new set per draw, so the list grew between pipeline binds and was walked on every draw.
5. **Push constants without copies:** the data (up to 128 bytes, a heap vector) was copied twice per `vkCmdPushConstants` (~400 per frame); now moved.
Tests: suite 29/29 in default, submit-thread + old bound-set behaviour, and with `RW_GPU_FPS_CAP=30 RW_GPU_THERMAL_GUARD=1`.

## v13.70 (2026-10-20) — fullscreen/borderless: 3 flip buffers and tearing (present no longer waits for the screen)
**Your map test (run 140535, v13.68):** windowed until ~160 s, then fullscreen (1920×1200) and briefly borderless, 2x speed from ~218 s.
- **Windowed:** the DXGI Present call 0.4–0.5 ms, frames 17 ms (60 fps cap) when not throttled; whole `vkQueuePresentKHR` 3–7.5 ms.
- **Fullscreen/borderless:** Present call **7–10 ms**, `vkQueuePresentKHR` **12–17.5 ms**, frame-time p95 **55–62 ms** (was 20 ms) — every other frame waited for the next screen refresh. That was the 12–17 ms "present" time found in v13.68, and the hiccups you saw in fullscreen.
- **Cause:** in fullscreen/borderless Windows shows the back buffers by flipping them directly (no desktop compositor). With only 2 buffers and no tearing permission, a flip-model Present waits for the display's refresh even with sync interval 0, and the next copy into a back buffer waits for the screen to release it.
- **Other hiccups in that run:** the 2.4–7.7 s stalls every ~20 s in the windowed part are the map test's own frame pictures (BMP dumps every 20 s; normal play has none). At 2x speed one 115 ms frame had 6 ticks (normal for the tick catch-up).

**Changes:**
1. **3 flip buffers** instead of 2 (`RW_GPU_FLIP_BUFFERS=2` = old): one buffer on screen, one queued, one free to draw into.
2. **Tearing allowed** when Windows and the driver support it (DXGI 1.5 `DXGI_FEATURE_PRESENT_ALLOW_TEARING`; flag `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING`, `Present(0, DXGI_PRESENT_ALLOW_TEARING)`): Present no longer waits for the screen refresh in fullscreen/borderless. Side effect: a horizontal tear line can be visible when the frame rate is not 60. `RW_GPU_ALLOW_TEARING=0` = off. Log: `[RW-GPU-WSI] tearing ...: supported, on / not supported`.
3. `envflags::number` helper.
4. **Menu: "Speed test (5 min, no pictures)"** on the Tests page: the quicktest map without frame diagnostics/shader dumps. Reason (run 144726, below): the map test's frame diagnostics cost 1.5–9 ms per frame inside vkQueuePresentKHR (`present.diag`) plus 2–8 s pauses every 20 s, so map-test frame rates understate normal play.

**v13.69 results (run 144726, v13.69 renderer; the summary header says v13.70 because VERSION.txt was updated while it ran):**
- **Freeing commands in the background works:** `vkResetCommandBuffer` **0.9–1.2 ms → 0.08–0.13 ms per frame** (19 million commands freed on the reaper thread).
- **Sub-page uploads:** 727k uploads without a write-watch query; `watch-query` 0.3 → 0.2 ms/frame; UploadMemory 8.6–11 µs → 5.9–7.5 µs per call (unthrottled windows).
- **Cleanup shape key:** kept cleanups 625k of 9.5M (6.6%; was ~17%).
- **Thread tuning active:** `[RW-OPT-THREADS] job workers set to normal priority: 3; render thread above normal: yes`. Present mode reported by the game: FIFO (the bridge presents without vsync wait).
- **Present split:** `present.lock` 0, `present.copy` ~0.2 ms, `present.Present` 0.2–0.7 ms windowed (3.8 ms in a fullscreen window of this 2-buffer build), **`present.diag` 1.5–9 ms = the map test's own diagnostics**. Normal play does not have that cost.
- Average while playing 55.3 fps, 1% low 16.8 fps (map test incl. diagnostics, CPU down to 46% at times).
Tests: suite 29/29 with the new defaults and with `RW_GPU_FLIP_BUFFERS=2 RW_GPU_ALLOW_TEARING=0`; test environment reports tearing supported, 3 buffers.

## v13.69 (2026-10-20) — review round: many small wins in the bridge and the optimizer mod (HD5500 Optimizer 0.3); 1 ms of command freeing moved off the render thread; present time split
**User request:** "review both the optimizer mod and our bridge for possible optimizations and performance wins. 10x 0.1 ms is still 1 ms off the total, so any small increment will be useful especially if they act cumulative". Two parallel code reviews (bridge hot paths; game-side knobs in the decompiled 1.7 sources), then the safe items implemented. Savings are estimates until the next map test; every change has a switch to restore the old behaviour.

**Bridge (renderer):**
1. **Sub-page uploads skip the write-watch query** (`RW_GPU_SUBPAGE_DIRECT=0` = old). A range that contains no whole page can never have its page reset, so after the first write `GetWriteWatch` always answered "dirty" — a ~2–5 µs system call bought nothing. Waylith's dynamic uniform windows (a few hundred bytes, 44–111 per frame) are copied directly now. The FRAMES `watch-query` figure (0.3 ms/frame in run 125009) should drop. Counter in `[RW-GPU-IA]`: "sub-page uploads without write-watch query". Est. 0.1–0.4 ms/frame.
2. **Post-submit cleanup keyed by descriptor-set *shape*** (`RW_GPU_CLEANUP_SHAPE_KEY=0` = old). After each command buffer the bridge nulls the slots it bound; duplicates are skipped by a key. The key contained the set handle, and Waylith uses a new set per draw, so hundreds of `unbindAll` calls ran after every frame. The key is now (layout, set index, per write: category, type, binding, array element, count, stages) — exactly what decides which slots are nulled. Est. 0.1–0.5 ms/frame.
3. **No re-resolve of the output-merger UAV list when a set without storage descriptors replaces another one without** (`RW_GPU_UAV_RESOLVE_ALWAYS=1` = old). The resolve allocates (shared_ptr, maps, layout comparison with two sorted vectors) and ran at the first draw after every set bind. Recording side, est. 0.1–0.5 ms/frame.
4. **Descriptor-bind timing with the time-stamp counter** instead of 4–6 `QueryPerformanceCounter` calls per bind (calibrated once against QPC). ~0.03–0.08 ms.
5. **`ID3D11DeviceContext1` asked once per context** instead of `QueryInterface`/`Release` around every buffer upload; `QueryPerformanceFrequency` once instead of per upload.
6. **Push constants:** buffer size asked from the driver once per buffer (was `GetDesc` per upload); only the tail beyond the data is zeroed (was memset of the whole buffer + copy).
7. **Recording:** dynamic offsets of a set bind assigned in place (no new vector per bind); the per-command no-op `fillContext` pass over all 2,000–12,000 commands removed; one device-health check before the cleanup actions instead of one per action.
8. **Recorded commands freed on a background thread** (`RW_GPU_DEFERRED_FREE=0` = old). Your v13.68 map test (run 140535) showed `vkResetCommandBuffer` at **0.9–1.2 ms per frame** on the render thread: it destroyed the previous frame's 2,000–12,000 heap-allocated commands. They now go to one below-normal-priority "reaper" thread; commands whose destructors return bridge objects to the device (blits, clears, staged texture copies) are still destroyed on the calling thread. At most 8 batches wait (then the caller frees itself). Counter in `[RW-GPU-IA]`: "commands freed in the background". Est. ~1 ms/frame off the bottleneck thread.

**Suggestion 1 (constant-buffer ring) — what the code review showed first:** Waylith's per-draw uniforms already arrive as *dynamic* uniform buffers in one host-visible ring, which the bridge binds with `*SetConstantBuffers1` + offsets (the DXVK-recommended path, since v13.4x). ## v13.60 (2026-10-20 night) — less recording work per draw; flip presentation model
**User request:** "Keep optimizing further and do more deep research on other ways."
**Review target this time: the recording side.** The bridge's measured time (4.9 ms/frame) only covers *executing* command buffers at submit. Recording (`vkCmd*` calls on the game's render thread) is counted in the game's own time and had per-draw heap work:

3. **Flip presentation model** (research: Microsoft "For best performance, use DXGI flip model"). Flip swapchains cannot share a window with another swapchain, so a replaced swapchain releases its DXGI swapchain first (`retireNative`, later presents to it return OUT_OF_DATE). If Windows refuses a flip swapchain, the old model is used automatically (`[RW-GPU-WSI] flip-model swapchain refused`); `RW_GPU_FLIP_MODEL=0` forces the old model. The log says which model is in use (`[RW-GPU-WSI] swapchain WxH, presentation model …`).

Microsoft's rule for `OMSetRenderTargetsAndUnorderedAccessViews`: "Two UAVs conflict if they share a subresource" (a buffer is one subresource) — and with any conflict the call is not passed to the driver at all. So every draw that needs two instance buffers from the ring lost both: all puffs got zero transforms and vanished. The forbidden X has only u1 → worked; thought bubbles are drawn one by one without instance buffers → worked. Why the `[RW-GPU-UAV-MISSING]` detector stayed silent: it checks the bridge's own bookkeeping, which said "bound"; the descriptor-set bind had sent both views (rejected by D3D11), and the draw-time resolve then saw "already bound" and skipped.
**Fix (`Miscellaneous/D3D11UavAlias.hpp`, new):** all graphics-UAV binds now go through `uavalias::bindOutput()` (descriptor-set bind, draw-time resolve, flush after hazards, subpass begin). Log: `[RW-GPU-UAV-ALIAS]` (first 4). Switch: `RW_GPU_UAV_ALIAS_COPY=0` = old behaviour.

**User request:** "continue enhancing the code and performance, search the internet for inspiration". **1. Texture binds no longer call getenv (the biggest find).** Every SRV a descriptor set binds goes through the hazard check `hazards::Tracker::writesOverlapping()` (does this texture overlap a render target or UAV that is being written?). ## v13.51 (2026-10-19 night) — bridge hot path: fewer state-cache flushes, no per-draw environment lookups; firmware-limit reading fixed
**User request:** "keep working on performance … find ways to improve performance on different levels … then start refactoring and optimise the code, and document everything properly." This version is the first refactoring/performance pass on the bridge's per-command path. No picture changes are intended; every change has a switch or is a pure caching of something that cannot change during a run.
**1. State cache no longer flushed on every swizzled texture bind (biggest item).** Background: since v13.39 the bridge remembers which shader resources, samplers and constant buffers are already set in D3D11 and skips repeated identical calls (`D3D11StateCache.hpp`). Any helper pass that changes the D3D11 context behind the cache's back must "invalidate" it (forget everything), after which every following bind is sent to the driver again. Vulkan image views with a non-identity component swizzle (e.g. R→RGB for single-channel textures; D3D11 has no swizzle) are emulated with a cached shadow texture (v13.14, `D3D11ImageViewSwizzle.cpp`); the shadow is redrawn only when the image's content version changes. ## v13.47b (2026-10-19 evening) — FIX: the forbidden X read its instance data from the wrong place in a shared buffer
**User report on v13.47 (game paused, survival packs forbidden):** shadows great, performance better, but **no red X at all** on the forbidden items. **Root cause (in Ashes, not the game):** Waylith uploads each draw's instance matrices into one big per-frame "storage ring" (`VulkanMeshDrawEncoder.TryUploadStorage`, decompiled) and gives the shader a descriptor `{ring buffer, offset N, range R}`. ## v13.47 (2026-10-19 evening) — FIX: forbidden X read the wrong instance buffer (UAV slot mix-up)
**Laptop evidence (v13.46, run 165317):** the new `inst-data` lines caught the X batch in the act. Frame 1800: an earlier instanced draw (shader with `_InstanceTransforms` u1 and `_Color` u2) left its 8 MB transforms buffer in UAV slot 1. The X draw (shader with only `_InstanceTransforms : register(u1)`) then had **the stale 8 MB buffer in slot 1** (all zeros where its matrices should be → 50 X quads collapse to nothing) and **its own 16 MB buffer one slot higher, in slot 2**, where its shader never looks. In frames 1386/1839/2870 the X buffer sat correctly in slot 1 and the X was drawn. That is exactly the "vanishes for seconds, then all X reappear" pattern, independent of the item state.
**Why it happened:** D3D11 has no descriptor sets; Ashes flattens (set, binding) into one running UAV index per *pipeline layout* and compiles each shader with `register(u<RTV count + index>)` taken from **the drawing pipeline's layout**. But at `vkCmdBindDescriptorSets` time it computed the slot from **the layout passed to the bind call**, and merged the result into whatever was bound before without clearing. Most likely Waylith binds its sets with a sibling layout (inferred from the slot pattern; the laptop summary will confirm it via the correction count) in which an earlier set holds one storage buffer more (real drivers and lavapipe address by set+binding, so the game never notices; Vulkan validation would). Result: the X buffer landed at index 1, the shader read index 0 = the previous draw's leftover buffer.
**Fix:** a new `ResolveOutputUavsCommand` is recorded in front of every graphics draw. It takes the descriptor sets currently bound (per set index), keeps only sets whose layout matches the drawing pipeline's set layout, gathers their storage buffers/images with **the drawing pipeline's own layout** (the same mapping the shader registers came from), and rebinds the complete output-merger UAV array — slots no longer used are cleared, including slots left above the range by render passes with a different target count (`uavAbsEnd`). The result is cached per (pipeline layout, bound sets) on the recording side, so the cost per draw is one map compare when nothing changed. Bindings missing from a layout are now skipped instead of an `assert` (undefined behaviour in release builds, 25 places). When the resolve corrects a wrong or stale slot it logs `[RW-GPU-UAV-RESOLVE] stale/misplaced UAV corrected: had[..] want[..]` (first 12), and the run summary counts them. Switch: `RW_GPU_UAV_RESOLVE=0` = old behaviour.

## v13.35 (2026-10-19 late morning) — FIX: vertex→pixel shader varyings line up by register (plants, likely marsh/water overlays)
**v13.34 experiment result:** with every sampler forced to mip 0, plants were still invisible → mip levels ruled out (experiment switched off again). The user also reports the **marsh** terrain looks wrong (flat grey-green block instead of the marsh texture).
**Cause:** D3D11 links the vertex shader's outputs to the pixel shader's inputs **by register position**, not by name. SPIR-V/Vulkan links by `location`. Waylith's plant shaders: the vertex shader (`PlantWindSway`) writes location 0 (colour), 1 (uv) and 2 (fall seed), but `CutoutPlant.frag` reads only locations 1 and 2. After translation the pixel shader's inputs start at register 0 while the vertex shader's uv sits in register 1 → the pixel shader read the **vertex colour as its texture coordinate**. Plant vertex colour is (0,0,0,0) (its alpha is the wind-sway weight), so every plant sampled the empty corner of the atlas and was discarded by the alpha test; the shadows (different shader) were fine. Any other shader pair where the fragment shader skips an output is affected the same way (candidates: marsh/water/terrain overlays, fleck/geyser effects).
**Fix:** when a graphics pipeline is created, the bridge reads the fragment shader's input locations and, while translating the vertex shader, moves every output the fragment shader does not read behind all read ones (location 32+n). HLSL interface structs are emitted in location order and fxc assigns registers in that order, so the read outputs now sit in exactly the registers the pixel shader expects (extra trailing outputs are legal). SPIRV-Cross's own `mask_stage_output_by_location` is ignored by its HLSL backend, hence the relocation. Generic: helps every Vulkan game on the bridge. Off switch: `RW_GPU_VARYING_MASK=0`.
**Regression test:** smoke mode `varying` — VS writes green at location 0 and blue at location 1, FS reads only location 1. Expected blue triangle (`209.1,0.0,45.9`); v13.34 draws it green (wrong register) — reproduced in the Wine emulator too. Emulator suite 17 checks, laptop self-test 17 entries.

## v13.33 (2026-10-19 morning) — FIX: vertex buffer bindings survive pipeline binds and render passes (colonists, animals, trees)
**Found with the v13.32 logging (run 090901):** every colonist/animal body draw uses two vertex bindings: binding 0 = the mesh (position, normal, uv; stride 40) and binding 1 = a small **per-instance "default attribute" buffer** (stride 48) from which the vertex **colour** (attribute at offset 16) is read. Waylith binds that buffer once and keeps drawing with it through many pipeline switches and render passes — legal in Vulkan, where vertex-buffer bindings are command-buffer state. The inherited Ashes code **cleared its vertex-buffer state** whenever a pipeline with a different vertex layout was bound (and at render pass begin/next/end), so D3D11 slot 1 kept whatever buffer an earlier draw had left there (the log showed stride 32 / offset 48 from an item draw while the pipeline expected stride 48). **Fix:** the command buffer now keeps a per-slot table of bound vertex buffers (as Vulkan does) and rebuilds the D3D11 binding from it before every draw with the current pipeline's strides (slots the pipeline does not describe get stride 0). No clearing on pipeline bind or render passes. This is a generic correctness fix for any Vulkan application on the bridge.

## v13.17 (2026-10-18 night) — push constants on a fixed slot (pawns, animals, trees)

## Engine / framework facts learned today (from decompiling `Waylith.dll` + public BRUTAL source)
- `Waylith.Graphics.GraphicsDevice`: instance API = min(1.2, loader); device API = min(instance, physical device). **Vulkan 1.0 devices are accepted**; SPIR-V target is 1.0 below Vulkan 1.1. Required device extension: only `VK_KHR_swapchain`. Optional: `VK_EXT_memory_budget`, `VK_EXT_full_screen_exclusive`, `VK_KHR_get_physical_device_properties2`, `VK_EXT_debug_utils`, video-decode set (`VK_KHR_synchronization2`, `video_queue`, `video_decode_queue`, `video_decode_h264`) only if all present. Device features requested only if supported: `fillModeNonSolid`, `samplerAnisotropy`, `dualSrcBlend`, `independentBlend`. VMA falls back to API 1.0 if `vkGet*MemoryRequirements2` are missing (the 15 Oct fix). Env var `WAYLITH_VULKAN_DEVICE=<substring>` picks the GPU.
- BRUTAL (RocketWerkz, `ahwootech/BRUTAL`, "BRUTAL License v1.0", MIT-like): a thin generated binding, enforces nothing; it resolves ~800 entry points eagerly via `vkGet*ProcAddr` and stores NULLs (an ICD must return NULL quietly), loads `vulkan-1.dll` from System32 only, ships `vma.dll` (VMA 3.4-dev, dynamic function fetch). README says "Vulkan 1.3 capable GPU" but that is guidance, not code. Upstreaming a compatibility layer there is not the lever; Ludeon is.

## v13.9 (2026-10-18 evening) — world-pass HDR resolve
**Problem:** "Generating world" froze with music playing. `Player.log` showed the bridge rejecting `vkCmdBlitImage` inside `SceneColorTargets.RecordResolveFrom`; the game's render thread then died silently.
**Cause (3 layers deep, all in Ashes):**
1. RimWorld renders the world into a 16-bit float HDR target (`VK_FORMAT_R16G16B16A16_SFLOAT`) and blits it, same size, into the 8-bit scene target (`B8G8R8A8_UNORM`, hard-coded by the engine). Ashes' compute-blit gate only allowed RGBA8/BC7 sources and an RGBA8 destination.
2. The scratch-size helper (`getCompactPayloadBytes`) only knew RGBA8 texel size.
3. A typed `B8G8R8A8_UNORM` UAV is rejected by the HD 5500 driver (`CreateUnorderedAccessView2D` failed), so even with the gate open the write view could not be created.
**Fix:** gate widened to float sources and the BGRA8/RGBA8/RGBA16F destinations; texel-size table; 8-bit destinations are now written through an `R32_UINT` UAV (mandatory on every D3D11 device) with byte packing in the shader; an unsupported combination now logs and skips one region instead of failing the whole command buffer (which is what killed the render thread).
**Status:** emu PASS all 6 modes incl. new `hdrresolve` (pixel-exact). Laptop: pending.
**Idea noted:** a draw-based (pixel-shader) blit would avoid UAV limits entirely and is the natural long-term path. Not needed yet.

## v13.8 — ClearAttachments + capture mode
**Fix:** `vkCmdClearAttachments` dereferenced a null depth view and left a malformed scissor (`{x,y,w,h}` instead of `{l,t,r,b}`) bound. The world pass calls this every slice. Old DLL null-faults on the emu `clearattach` mode.
**Added:** `-Capture` / `Play-RimWorld-Record.cmd` (GFXReconstruct layer, untested on laptop). Known limit: D3D11 clears cannot be clipped to a sub-rect.
**Status:** emu PASS; laptop menu regression PASS (37 fps, 149 s, clean exit).

## v13.7 — swapchain rebuilt every frame (~5 → ~37 fps)
**Cause:** surface `currentExtent` came from `GetWindowRect` (incl. title bar). Waylith compares it with GLFW's framebuffer size every frame and rebuilt the swapchain on every mismatch.
**Fix:** `GetClientRect`. **Added:** `-QuickStart` play mode, `Play-RimWorld*.cmd`.
**Status:** laptop PASS (1 swapchain for 5,400 frames).

## v13.6 — world-generation access violation
**Cause:** `BeginRenderPassCommand` indexed `clearValues[attachment]` for every attachment; RimWorld passes 0 clear values for its LOAD-only world pass (valid Vulkan). Only an assert guarded it.
**Fix:** zero-filled per-attachment clear array; also fixes wrong clear colour when a LOAD attachment precedes a CLEAR one.
**Status:** emu PASS (`loadpass`); laptop: the crash no longer reproduces (superseded by the v13.9 freeze further along).

## v13.5 — black screen
**Cause:** `PushConstantsCommand` used `Map(WRITE_DISCARD)` then wrote only the current range, wiping earlier `vkCmdPushConstants` ranges. Scale became 0; every UI vertex collapsed.
**Fix:** CPU shadow of the whole block, full upload each time.
**Status:** laptop PASS (menu visible and clickable).

## Decisions and dead ends
- **Dozen (Vulkan-on-D3D12): ruled out.** HD 5500 D3D12 = Shader Model 5.1, binding tier 1; Dozen needs SM6/DXIL. Tested 24.3.4, 25.3.6, 26.1.8, 26.2.4: all crash at device/pipeline creation.
- **WSL: ruled out.** No direct GPU access; would route through Dozen anyway.
- **Modded Windows Vulkan drivers: none exist for Broadwell.** Intel's `igvk64.dll` starts at Skylake; the OEM 20.19.15.x packages contain no Vulkan component.
- **D3D11 vs D3D12 backend:** D3D11 is the stronger backend on this GPU (FL 11_1, mature). No reason to add D3D12.
- **Linux (Mesa hasvk):** real Vulkan 1.3 on this GPU; kept as the fallback/alternative track (live USB needs no disk space on C:).
- **Steam "RimWorld" grant vs. the real exe:** the launcher starts `RimWorld.exe` directly; a desktop shortcut to the exe made the game window grantable for computer use.
