## Findings used in this session
- **D3D11 UAV conflict rule [Verified]** (Microsoft, OMSetRenderTargetsAndUnorderedAccessViews): "Two UAVs conflict if they share a subresource"; with any conflict the call is not passed to the driver. A buffer is one subresource → binding one buffer to two UAV slots leaves every UAV slot empty. This is the geyser-steam bug fixed in v13.53.
- DXVK guidelines: redundant state and per-draw vertex-buffer binds are the classic CPU cost; deferred contexts only with few large command lists.
- NVIDIA "Constant Buffers without Constant Pain": a constant-buffer update between draws cuts the possible draw rate ~8×; Map(DISCARD) ≈ 256 cycles per bound stage.
- Intel "Understanding DirectX Multithreaded Rendering Performance by Experiments": Intel supports concurrent creates, **not** driver command lists; on few cores single-threaded immediate rendering beat deferred multithreading.
- RimWorld 1.7: mods target .NET 10 and Harmony 3.0; Prepatcher-based performance mods (Performance Fish, RocketMan) are presumably not 1.7-ready. Dev mode has a Frame Profiler (useful to split game vs. bridge time).

## More ways (researched 20 Oct 2026, second pass)
- **DXGI flip model [Verified, Microsoft]**: blt presents copy into a surface owned by the window; flip shares the buffer with the compositor ("minimal copies", better performance, lower power); with matching size the compositor can be bypassed (DirectFlip / independent flip) and latency can reach 1 frame. Requirements: ≥ 2 buffers, no MSAA, re-bind the back buffer after Present; blt only needed for HWND interop (several APIs/swapchains in one window). → **Implemented in v13.60** (fallback to blt automatic).
- **Recording overhead**: per-draw heap allocations in the ICD's `vkCmd*` path are invisible in the bridge's execute timer but cost the game's render thread → **v13.60** shares vertex bindings and drops repeat upload commands.
- **.NET runtime knobs [Verified, .NET docs]**: tiered compilation, quick JIT, ReadyToRun mainly affect start-up; tier-2 + TieredPGO steady state (default on). Nothing to gain for frame rate; GC already measured at ≤1% of the time.
- **Remaining big factor**: CPU clock averages ~70% of nominal in every run (lowest 46–66%) — Windows power plan / Lenovo firmware limits. Shown on the "Laptop health" page; the bridge does not change system settings.
- **Still open**: ResolveOutputUavs per draw (record-time skip needs care: render-pass begin and descriptor binds change the context), constant-buffer ring with `NO_OVERWRITE`, shader compiles on a worker thread (first-use stutter only).

## Bridge and RimWorld: what is left (review + research, 20 Oct 2026, fourth pass)
- **Where the frame goes now (Normal speed):** simulation ticks ~1.1 ms, world/map update ~1.6 ms, bridge execution ~10 µs per draw (3–5 ms), present 0.2 ms (flip model), the rest is the game's UI/render code and waiting for its 60 fps limit. Lighter maps reach the limit; heavier maps (450+ draws) run at ~50 fps. v13.62 adds the recording time per frame to separate the game's render code from everything else.
- **Bridge candidates, by expected gain:** (1) per-draw descriptor work — `BindDescriptorSet` ~1.8 µs and `ResolveOutputUavs` ~3 µs where the binding changes; a record-time skip needs care because render-pass begin and helper passes change the output-merger state; (2) one constant-buffer ring with `NO_OVERWRITE` instead of per-UBO updates; (3) the per-command loop overhead (timing + virtual call, ~0.3 µs × 2,300–12,700 commands); (4) shader compiles on a worker thread (first-use stutter only).

## Fifth pass (20 Oct 2026): long research, five ranked suggestions
Matched against our own laptop measurements (Normal speed: bridge ~10 µs per draw, 300–480 draws and 2,300–12,700 commands per frame, present 0.2 ms, CPU at ~70% of nominal with dips to 22%).

1. **[v13.63: done in the form the code needed — per-draw uniforms already use one ring + `*SetConstantBuffers1`; the push-constant bookkeeping was the cost and is now ~10× cheaper]** **One constant-buffer ring with `MAP_WRITE_NO_OVERWRITE` + `*SetConstantBuffers1` offsets for push constants and per-draw uniforms.** DXVK developer guidelines: binding sub-ranges of a large buffer with `*SetConstantBuffers1` is "by far the fastest path"; map with DISCARD only a few times per frame and write as much as possible each time. NVIDIA/McDonald "Efficient Buffer Management": 115 per-call Map/Unmap = 4.36 ms per frame → batched DISCARD 0.27 ms → triple-buffered NO_OVERWRITE ring 0.22 ms ("most of the savings came from reducing API calls"). Bridge today: one small constant buffer per push block, updated per change (190–360 k uploads per session). Expected: 0.5–1.5 ms per frame less bridge time on heavy maps. Effort: medium.
2. **[v13.63: done — descriptor-set fast path at execution time, safer than record time]** **Skip redundant per-draw binds in the bridge (descriptor sets, output-merger UAVs) with record-time state tracking.** DXVK: "Re-binding a large number of vertex buffers on every draw call can quickly become the primary CPU bottleneck"; batch draws with the same state. Our profile: `BindDescriptorSet` ~1.8 µs, `ResolveOutputUavs` ~3 µs where it changes, recorded per draw. Index/vertex buffers already cached (v13.58/v13.60). Expected: 0.5–1 ms per frame. Effort: medium, needs care around render-pass begin and helper passes.
3. **Pre-compile shaders from the disk cache during loading.** DXVK: compile shaders during loading screens; on-demand compiles "cause stutters more severe than on native drivers". Bridge: the HLSL bytecode cache already exists (41/41 hits on later starts) but entries are only loaded when the game first uses a shader. Pre-creating all cached shader objects on a background thread at device creation removes first-use hitches when new things appear on screen. Effort: small–medium.
4. **Register the render/submit thread with MMCSS "Games" (`AvSetMmThreadCharacteristics`), opt-in next to the priority option.** Microsoft: MMCSS raises a registered thread into the 16–22 band while the app is in the foreground, with a guaranteed reserve for background work (SystemResponsiveness). Process-local, reverted with `AvRevertMmThreadCharacteristics`, no system setting changed. Expected: fewer short stalls when background programs wake; no average-fps gain. Effort: small.
5. **Cooling and memory (user's hardware, no software change):** the CPU averages ~70% of nominal clock in game with dips to 22% — heat. An i5-5200U thread on TechPowerUp traced 60→30 fps drops to the CPU reaching 100–102 °C; dust cleaning, fresh thermal paste and a cooling pad are the standard fixes (undervolting is the user's own decision and often blocked on these chips). Second: check that two memory modules are fitted (single channel costs the HD 5500 ~38% in GPU-bound games, pcbuildadvisor). The Laptop health check shows both.

Also found: flip-model independent flip needs the swapchain to match the screen; the game's window client area is 1920×1177 on a 1080-line screen (Ludeon report 3.17), so the compositor is still used — a possible later test (present a monitor-sized buffer).

## Seventh pass (20 Oct 2026): cheaper D3D11 calls per draw
User request: "Keep optimizing with possible fallback for the smallest increases. Look on the internet for more ideas." Labels as above. No source publishes Intel Gen8 D3D11 per-call costs; vendor numbers below are NVIDIA's.

- **Small per-draw uploads.** NVIDIA "Constant Buffers without Constant Pain": DrawIndexed ≈36 cycles, *SetConstantBuffers ≈114, Map(DISCARD)+Unmap ≈256, UpdateSubresource ≈214; recommends one big buffer, NO_OVERWRITE appends, `*SetConstantBuffers1` offsets [V]. AMD/NVIDIA "DX11 Performance Reloaded": UpdateSubresource is the sub-optimal path for frequent updates; set multiple slots in one call; multiple DISCARD maps per frame can stall [V]. DXVK developer guidelines: MAP_WRITE_NO_OVERWRITE between draws is fine; map "a few times per frame" [V]. Dawn commit 60a7ed16: on Intel Gen12, CopySubresourceRegion stalled where UpdateSubresource did not, so a ring + copy back into a DEFAULT buffer is risky on Intel; bind the ring directly [V]. Our UpdateSubresource1 windows cost 6–12 µs each (~30× NVIDIA's figure) [measured]. → **v13.73 merges the windows of one buffer per recording** (fewer calls, same API); a DYNAMIC NO_OVERWRITE uniform ring bound with `*SetConstantBuffers1` is the next, bigger step.
- **Lazy, ranged binds.** ANGLE dirty bits + `syncState` apply accumulated state at draw time [V]; "set multiple resource slots in one call" [V]. In RimWorld most binds touch one slot per stage, so ranged calls would save little; the real cost was that every bind walked the whole set because Waylith allocates a new set per draw → **v13.73 content fast path**.
- **BeginRenderPass**: DXVK — clear or discard on first bind saves CPU work; Intel 4th-gen guide — small copies and clears are expensive [V]. Only 3 passes per frame (0.16 ms): low priority.
- **D3D11_CREATE_DEVICE_SINGLETHREADED**: documented as "can increase performance" but undefined behaviour from several threads [K]; our prewarm, reaper and optional submit threads call the device → not applicable. No measurements found.
- **2C/4T scheduling**: Intel's multithreaded-rendering experiments — driver is ~55% of CPU once app hotspots are gone; deferred contexts slower on Intel (no driver command lists) [V]. MMCSS "Games" task and SetThreadIdealProcessor: only anecdotal evidence for pacing [U]; not added (the optimizer mod already raises the render thread's priority).
- **timeBeginPeriod**: per-process since Windows 10 2004 [V]; the bridge's cap already waits on a high-resolution waitable timer (v13.71).
- **Structural idea from our own counters**: 495 index-buffer switches per frame at ~1.8 µs, because every map section has its own index buffer; one D3D11 buffer per VkDeviceMemory block (with offsets folded into firstIndex, v13.66 machinery) would remove most of them. Large change; not started.

## Ninth pass (21 Oct 2026): findings from the Fracture sessions (same laptop, other engines)
- **D3D12 on the HD 5500 = feature level 11_1 but resource binding tier 1.** Limits: ≤8 UAVs across all stages, all descriptors in a bound table must be valid (null descriptors for unused slots), lower SRV/CBV/sampler caps. wgpu and Dawn reject tier 1; SDL3 GPU (3.2+) accepts it with `SDL_PROP_GPU_DEVICE_CREATE_D3D12_ALLOW_FEWER_RESOURCE_SLOTS_BOOLEAN` (≤8 storage resources). Relevance: none for the current D3D11 bridge; a rule set to follow if a D3D12 path is ever added.
- **Mesa Dozen** (Vulkan on D3D12, mesa-dist-win): a possible second Vulkan route. v13.77 adds `-AltIcd` / "Compare: other Vulkan driver" so it can be tried without changing anything. Expectation: probably fails on tier 1 or misses features Waylith needs; Fracture's `vulkan_dozen` test will tell for driver 20.19.15.5171.
- **D3D12 debug layer** needs the Windows optional feature "Graphics Tools"; the same feature provides the D3D11 debug layer used by `RW_HD5500_D3D_DEBUG_LAYER=1`.
- **OpenGL on this driver** (no `GL_EXT_texture_shadow_lod`, storage-buffer limits, presentation composed through GDI copy) and **ANGLE** (GLES→D3D11): not used by RimWorld 1.7, noted for completeness.
- **Benchmark hygiene** (wall-clock timing, Basic Render Driver check, invariant culture, `Win32_Processor` always reading 100%): all already handled in the bridge tools.
