# Running RimWorld 1.7 on pre-Vulkan GPUs: findings from a Vulkan→Direct3D 11 bridge on Intel HD 5500

**To:** Ludeon Studios, RimWorld 1.7 / Waylith engine team
**From:** an independent player and engineer
**Date:** 18 October 2026 (updated 21 October 2026 with bridge v13.77)
**Source and builds:** https://github.com/Liquidfiregamedev/hd5500-gpu-bridge (public; no game files included)

Your 12 October announcement said PCs older than about ten years may not run 1.7 and asked for reports. I got 1.7 running at a playable frame rate on a 2015 laptop that has **no Vulkan driver at all**. It runs through a Vulkan 1.0 → Direct3D 11 translation layer, with no game files changed. That exercised the engine's Vulkan 1.0 path end to end and showed exactly which engine habits are hard on weak or unusual drivers.

The first part of this report lists **what Waylith could change**, as two tables:

- **Part A:** changes that make 1.7 run on more graphics cards.
- **Part B:** general optimizations that help every slow PC.

Each row links to the details and measurements in section 3. Sections 1–3 are the evidence.

## Part B. General optimizations (every PC, measured on a 2-core laptop)

On this class of PC the **CPU decides the frame rate**: the GPU is busy for only 3–10 ms of a ~22 ms frame. Draws, descriptor work and command recording matter far more than shader cost.

| # | Change in the engine | Measured effect / why | Effort | Details |
|---|---|---|---|---|
| B1 | Bind the per-frame uniform buffer once as `UNIFORM_BUFFER_DYNAMIC` in a long-lived set and pass each draw's window as a dynamic offset. Today `TryUploadUniforms` allocates and writes a new descriptor set per draw only because the offset changed. | ~2 million set binds per session, nearly all new set objects. When the bridge recovered this itself (content compare + one uniform ring), its cost dropped from 2.3 to **1.2 ms/frame** and the 1% low rose from 9 to **21 fps**. Natively it removes per-draw `vkAllocateDescriptorSets`/`vkUpdateDescriptorSets`. | Medium | 3.16 |
| B2 | Sub-allocate map-section index (and vertex) data from a few large buffers; select sections with `firstIndex`/`vertexOffset`. | ~495 index-buffer switches per frame. The bridge's index pool cut them to ~25,000 per 5-minute session and its cost from 3.3 to 2.3 ms/frame. | Medium | 3.15 |
| B3 | At far zoom, merge distant map sections into fewer meshes and skip objects below a size on screen. | Zoomed out: ~820 draws, 500 set binds, 700 index binds per frame; 33–45 fps against 60 zoomed in. | Medium | 3.15 |
| B4 | Re-use recorded command buffers (or secondaries) for unchanged static content, and record independent passes on worker threads. | Recording is ~12 ms of the render thread's frame on an i5-5200U, against 3–6 ms to execute it. | Medium–large | 3.17 |
| B5 | Call `vkFlushMappedMemoryRanges` for the written ranges (or use non-coherent memory with flushes). | The draws reference 310–450 MB/s of host-visible ranges, but only ~5.7 MB/s changes. Native drivers ignore the flush for coherent memory; layers and remote or virtual GPUs get exact ranges for free. | Small | 3.14 |
| B6 | Create all pipelines during loading (or in the background with a `VkPipelineCache` saved to disk). | Removes the hitches the first time a raid, fire or weather effect appears. | Small–medium | 3.22 |
| B7 | Time-budget the simulation per frame (allow more ticks when fps is low), make the 45 ms tick budget adjustable, and spread rare/long ticks over several ticks. | Below ~30 fps, speed 3 can't reach its target however fast the CPU simulates. Most frames over 50 ms at Ultrafast contain ~29 ticks. | Small–medium | 3.24, 3.25 |
| B8 | Make the GPU probe fit its 1.5 s budget on slow GPUs (scale the group count down), cache an "incomplete" result, and skip it until something reads the tier. | ~1.7 s of full GPU load plus 272 MB of buffers on **every** boot on slow GPUs. | Small | 3.20 |
| B9 | Offer a 30/45 fps cap in the graphics settings. | On thin laptops, sustained 60 fps leads to thermal throttling (CPU at ~20% clock, multi-second stutters). 45 fps stayed smooth in the measured run. | Tiny | 3.31 |
| B10 | Clamp the window client area to the monitor work area. | The swapchain was recreated at 1920×1177 on a 1080-line screen: extra fill rate, and no compositor bypass. | Tiny | 3.19 |
| B11 | Add a frame-time / 1%-low readout to the developer Frame Profiler. | Makes player performance reports comparable. | Small | 3.25 |
| B12 | Bake low-resolution plant textures (64×64, no mips; 445 of 2,693 thing textures) at a higher resolution with mips. | Visual quality: aliasing and softness on agave and saguaro. | Small | 3.26 |

Robustness items with no performance angle:
- Treat a failed `vkEndCommandBuffer` or `vkQueueSubmit` like device lost, with a message (3.18).
- Warn on swapchain rebuild storms (3.19).
- Use `setlocale(LC_NUMERIC, "C")` for native code, and the decimal-separator save issue (3.23).

## 1. Background: how this was found

**Machine:** Lenovo Z70-80, i5-5200U, Intel HD 5500 (Broadwell, device 0x1616), driver 20.19.15.5171, Windows 10 22H2, 16 GB RAM. Direct3D 11 feature level 11_1; Direct3D 12 only Shader Model 5.1. Intel ships no Vulkan driver for this GPU on Windows.

**Approach:** a Vulkan 1.0 installable client driver translating to D3D11, built from the open-source Ashes project's D3D11 backend plus a compatibility loader proxy. The engine sees an ordinary Vulkan 1.0 device with `VK_KHR_swapchain`. No game files are modified.

**Latest measurement (bridge v13.75, 21 October, quicktest map, 5-minute automatic run, 45 fps cap):** 44.3 fps average against the 45 fps cap, **1% low 21.5 fps, 12 frames over 50 ms**. The translation layer costs **1.2 ms per frame (3.7 µs per draw)**. The same run on v13.72 measured 34.8 fps, a 1% low of 9.0 and 181 frames over 50 ms, at 3.3 ms per frame (7.2 µs per draw).

**Earlier result (bridge v13.61–v13.64, 20 October, 60 fps limit):** everything we have checked renders like the Mesa lavapipe reference: menu, world generation, portraits, the colony map with terrain, rocks, items, rivers, water, shadows, colonists, animals, all vegetation, forbidden-item markers, thought bubbles and geyser steam / dust puffs. At Normal speed on the quicktest map the game runs at **52–58 fps average (1% low 15–21 fps, 99% of frames under 26–29 ms)** and reaches its 60 fps limit on lighter maps; the translation layer costs about 10 µs per draw (3–5 ms per frame, down from 18 ms per frame four days ago). Every visual defect found on this machine was in the translation layer, not in the engine, except low-resolution plant textures in the asset pack (3.26). History: four days ago colonists, animals and vegetation were invisible and water and geyser smoke were missing; on RimWorld 1.6 (Unity) the same laptop rendered everything correctly.

**The engine's Vulkan 1.0 path works.** The log confirms it: effective version 1.0, "shaders will be compiled for spirv_1_0 and baked shader packs will not be used", VMA falling back to the 1.0 memory entry points. Every freeze and crash along the way was a gap in the bridge, not invalid Vulkan from the engine. Several engine choices are nevertheless legal Vulkan that is unusually expensive or fragile to emulate; Section 3 lists them with cheap suggestions, together with measurements of frame pacing and simulation speed on this hardware.

What the bridge had to add or fix, in order of appearance:

## 2. The hardware population that cannot get Vulkan on Windows

Facts about drivers, independent of anything Ludeon does:

- Intel's Windows Vulkan driver begins with Skylake (Gen9). Ivy Bridge (HD 4000), Haswell (HD 4200–5200) and Broadwell (HD 5500/6000) have no Vulkan on Windows from any source; the OEM 20.19.15.x packages contain no Vulkan component, and no modified drivers exist.
- The same silicon gets Vulkan 1.3 on Linux through Mesa's `hasvk`. The hardware is capable; the Windows driver was never written.
- Microsoft's Vulkan-on-D3D12 layer (Dozen) needs Shader Model 6. HD 5500's D3D12 stops at SM 5.1 and resource binding tier 1 (at most 8 UAVs, every descriptor in a bound table must be valid); wgpu and Dawn also refuse tier 1, so Dozen crashes at device or pipeline creation (Mesa 24.3.4 through 26.2.4 tested). WSL routes through Dozen too.
- The Steam page still lists Intel HD Graphics 4000 and Windows 7 as minimum. .NET 10 needs Windows 10 1607+, and Vulkan excludes that GPU entirely, so the listing is unachievable by any means.
- Public failure reports I found: HD 5500, HD 4600, GeForce GT 520MX (no Vulkan driver); Radeon R9 290X/390 crashing at startup (these have Vulkan drivers, so a different problem). The Modder Primer's "Vulkan 1.2 (fallback to Vulkan 1.0 attempted)" is accurate to the code, but players cannot tell what it means for them.
- The same approach should cover most of that population: the bridge needs only Direct3D 11 feature level 11_0, which Intel Ivy Bridge/Haswell/Broadwell, NVIDIA Fermi (GeForce 400/500, whose Windows Vulkan driver was never shipped) and AMD TeraScale 2 (HD 5000/6000) all have. Only the HD 5500 has been tested; since bridge v13.65 every run logs the GPU's feature level, missing capabilities ("DEGRADED") and a verdict, so reports from such machines can be read at a glance. Sandy Bridge (HD 2000/3000, feature level 10_1) is out of reach.

### 2.1 Hardware cases in the 1.7 #bug-reports forum (read 19–21 October)

|---|---|---|

Two patterns stand out. First, "has no Vulkan" and "has Vulkan, but the driver is too old to run 1.7" look identical to the player, and the fix is completely different (3.27). Second, the ~2012–2015 laptop population splits cleanly by vendor and generation:

- Intel Gen7–Gen8 and NVIDIA Fermi have no Vulkan.
- AMD GCN 1–3 and NVIDIA Kepler have Vulkan, but only on drivers that are often years newer than the OEM's.

For completeness: BRUTAL enforces no Vulkan version. It loads `vulkan-1.dll` from System32 only, resolves about 800 entry points eagerly and tolerates NULLs; its README's "Vulkan 1.3 capable GPU" is guidance, not code. The gate is Waylith's `GraphicsDevice`, and it is permissive: instance API `min(1.2, loader)`, device API `min(instance, device)`, only `VK_KHR_swapchain` required, `fillModeNonSolid` / `samplerAnisotropy` / `dualSrcBlend` / `independentBlend` requested only when supported. That design is why the bridge works at all.

## 3. Details and evidence for Parts A and B

Each item is valid Vulkan unless stated otherwise. Each suggestion is a small change that makes a minimal 1.0 implementation (a translation layer, an old Mesa driver, a mobile part) more likely to work, usually at no cost on native drivers. Items are grouped by topic; "information" items need no change and are there so a report from unusual hardware can be recognised quickly. Numbers come from the bridge's own counters on the HD 5500 laptop (frame statistics, per-command profiling, a read-only counter mod for ticks, .NET GC and frame phases) unless a source is named.

### 3A. Formats, transfers and fixed-function state

**3.1 HDR resolve via `vkCmdBlitImage` into a hard-coded format.** `SceneColorTargets.RecordResolveFrom` blits the float world target, same size, into `B8G8R8A8_UNORM`. Blit is the one transfer command with no D3D11 equivalent, and its format support is optional per format (`VK_FORMAT_FEATURE_BLIT_SRC/DST`). *Suggestion:* resolve with a full-screen sampled draw (a `BlitExact` material already exists) or a render-target resolve, and take the LDR format from the swapchain's reported list.

**3.2 Mip generation.** `Mipmapper.SupportsComputeMipmaps` is true only for `R8G8B8A8_UNORM`; `R8_UNORM`, `R16G16B16A16_UNORM`, `R32_SFLOAT`, `R32G32_SFLOAT` and `R32G32B32A32_SFLOAT` get scaled linear blits inside the same image, mip N to N+1. *Suggestion:* query `vkGetPhysicalDeviceFormatProperties` for `BLIT_SRC | BLIT_DST | SAMPLED_IMAGE_FILTER_LINEAR` (and `STORAGE_IMAGE` for the compute path) before choosing, with a draw-based or CPU fallback. The same query lets you use the compute path for more formats on capable hardware.

**3.3 Clearing sampled-only images.** `GpuTextureService` clears new `TRANSFER_SRC | TRANSFER_DST | SAMPLED` images with `vkCmdClearColorImage`. *Suggestion:* add `COLOR_ATTACHMENT` usage to images you intend to clear, or upload from a zeroed staging buffer.

**3.4 Partial clears of large atlases.** Each pawn is rendered into its 128×128 cell of the pawn atlas by a render pass with `LOAD_OP_CLEAR` and the cell as render area (the same issue applies to `vkCmdClearAttachments` with a rectangle). Valid and cheap on native Vulkan. Translation layers have to emulate it: D3D11 clears cover the whole view (D3D11.1 `ClearView` takes rectangles, but only for colour), and OpenGL ES/WebGPU-style backends behave similarly. A layer that gets this wrong leaves only the last pawn in the atlas, so every other colonist draws as an empty silhouette, while portraits (separate small targets) look perfect. That combination makes the bug easy to misdiagnose as a shader or texture problem. *Suggestion:* none required; if convenient, clearing a cell by drawing a transparent quad with the atlas material path, or clearing the whole atlas once per rebuild, avoids the partial clear entirely. Mentioned mainly so a pawn-silhouette report from an unusual driver can be recognised quickly.

**3.5 Blend factors.** `BlendState.MultiplyDestination` and the Unity-ported `Blend DstColor Zero` materials put `SRC_COLOR` / `DST_COLOR` in the alpha slots. Vulkan allows it; D3D11 rejects the whole blend state. *Suggestion:* use `SRC_ALPHA` / `DST_ALPHA` there. The result is identical by definition and the state is legal everywhere.

**3.6 Single-channel textures with view swizzles.** Opaque greyscale textures become BC4 or R8 with `(R,R,R,ONE)` in `VkImageViewCreateInfo::components`. D3D11 cannot express this; the bridge keeps a shadow RGBA copy per swizzled view, costing memory and a pass on every change. `VK_KHR_portability_subset` exists precisely so an implementation can report `imageViewFormatSwizzle = false`. *Suggestion:* honour that flag when present and then keep such textures RGBA, or apply the swizzle in the sampling shader.

**3.7 GPU block-compression encoders.** Atlas pages are BC7-compressed at bake time by a compute kernel (`TextureBlockEncoder`, `EncodeBC7Fast.comp.hlsl`); `-texFormat`, `-noCompressAtlases` and `Prefs.TextureCompression` already exist. *Suggestion:* document those switches, and add a one-time self-test (encode a known 4×4 block, read it back) that disables the GPU encoder on mismatch. A black-texture bug on an odd driver then becomes a logged downgrade.

### 3B. Shaders, descriptors and storage buffers

**3.8 Descriptor stage flags wider than the shaders that read them.** Some set layouts mark uniform buffers as visible to vertex and fragment stages when only one stage declares them. Legal Vulkan, and free on native drivers, but every layer that maps bindings to per-stage slots has to bind them for both stages, and an unread binding can collide with something the stage does read (here, the push-constant block that carries the model matrix; pawns, animals and trees disappeared until the bridge pinned push constants to a fixed slot). *Suggestion:* derive each binding's `stageFlags` from shader reflection (Slang already provides it), so layouts only expose a binding to stages that use it. It also reduces descriptor work on every driver.

**3.9 Keep instance buffers `readonly`, and make the remaining writable one read-only.** Waylith already declares its instance buffers `readonly`, which is what let the bridge skip a GPU-to-CPU copy after every instanced draw (the single largest frame-time cost on this laptop until fixed). Please keep that qualifier in new shaders and in Slang output; translation layers and some mobile drivers use it to decide whether host-visible memory must be synchronised back. The instanced path (`Graphics.DrawMeshInstanced` → `_InstanceTransforms`) reads per-instance matrices from a storage buffer that the vertex shader does not declare `readonly`/`NonWritable`. On D3D-based translation layers a writable buffer in a vertex shader has to become an output-merger UAV, which shares slots with render targets and is silently unbound by unrelated render-target changes; on this laptop that made every forbidden-X overlay vanish for seconds at a time until I added a save/restore. Declaring the buffer read-only in the shader (as the other instance buffers already are) would let layers bind it as a plain shader resource and avoid the whole class of problem. Related: storage buffers read in the vertex shader map to a D3D11 structured-buffer SRV at feature level 11_0 only when read-only; writable ones need 11_1, so please keep the common path read-only.

**3.10 Two storage-buffer descriptors into one buffer in the same draw.** Instanced fleck/mote batches read `_InstanceTransforms` and `_Color` from one storage ring at two offsets. Valid Vulkan, but D3D11 (and any layer on top of it) cannot bind one buffer to two UAV slots: the whole bind is rejected and the batch disappears (geyser steam, dust puffs on this setup). Declaring these storage buffers `readonly` in the shaders (they are only read) would let layers bind them as shader resource views, where aliasing is allowed — and is free on native drivers. **Confirmed 19 Oct:** with the bridge's fix switched off, Microsoft's D3D11 debug layer reports "OMSetRenderTargetsAndUnorderedAccessViews: The UnorderedAccessView at slot 1 overlaps with the UnorderedAccessView at slot 2" and the steam disappears; with private copies for the second slot it renders on the HD 5500 and on WARP.

**3.11 Fragment shaders that skip vertex outputs.** `CutoutPlant.frag` consumes locations 1 and 2 of `PlantWindSway.vert` but not 0. Legal in Vulkan; D3D-based translation layers (and some older GL drivers) link varyings by register and need the stages' interfaces to line up. Declaring `layout(location = 0) in vec4 vColor;` in the fragment shader (unused) would make the pair robust at zero cost.

**3.12 Descriptor sets bound with a non-matching pipeline layout, and ring sub-allocation.** The v13.46 diagnostics showed the forbidden-X instance buffer arriving in the wrong UAV slot most likely because sets are bound with `vkCmdBindDescriptorSets` using a pipeline layout whose earlier set layouts differ from those of the pipeline that then draws (one storage buffer more in an earlier set). Vulkan only keeps set N valid across layouts when sets 0..N are identically defined ("pipeline layout compatibility"); native drivers that address descriptors by set+binding tolerate it, but translation layers that flatten bindings per layout (Ashes, and likely others) place the buffer one slot off. The validation layer reports this as a VUID on the bind or draw. Binding with the drawing pipeline's own layout (or keeping shared set layouts identical across sibling layouts) avoids it. The bridge now works around it by resolving slots at draw time (v13.47). The forbidden-X fault turned out to be a translation-layer bug: Ashes ignored `VkDescriptorBufferInfo.offset/range` for storage buffers, while Waylith (correctly) sub-allocates every draw's instance data from one per-frame storage ring. Nothing for Ludeon to change there; it may still be useful to know that ring sub-allocation of storage buffers exercises a code path some layers get wrong. The layout point above stays as a hypothesis only: with set layouts compared by definition, no mismatch has been proven yet.

**3.13 The once-bound default-attribute vertex buffer (information).** Waylith binds a small per-instance buffer that supplies default vertex colour/normal/uv once and then draws with many pipelines. This is correct Vulkan, but it is exactly the pattern that exposed a bug in the translation layer used here (it reset vertex-buffer state on pipeline binds). Engines targeting weak or translated drivers sometimes re-bind such buffers per pipeline for robustness; it costs nothing on real drivers. Not a request — just a note on where the long-standing "invisible colonists" came from.

### 3C. Memory, uploads and command recording

**3.14 Persistently mapped coherent rings.** Waylith keeps its large upload rings persistently mapped in HOST_COHERENT memory and never calls vkFlushMappedMemoryRanges. That is valid Vulkan, but a translation layer to an API without shared CPU/GPU memory cannot tell what changed and has to diff or re-copy whole rings each frame (here 118–190 MB/s before the bridge used OS write tracking). A non-coherent memory type with explicit flushes of the written ranges — or simply a flush call, which native drivers ignore for coherent memory — would give layers the exact ranges at no cost on native drivers. **Measured (20 Oct):** the draws of one frame reference 310–450 MB/s of host-visible ranges, but only about **5.7 MB/s actually changed** (OS write tracking, 4 KiB pages). An explicit flush of the written ranges would hand that difference to every layer for free.

**3.15 Draw count and per-draw work in the recorded command stream (corrected 20 Oct).** A typical frame command buffer holds **300–480 draws and 2,300–12,700 commands** at normal zoom. An earlier version of this item said that almost every draw re-binds an unchanged index buffer; bridge v13.66 counted every index-buffer bind in a full map test and that is **not** the case: of 2.3 million `vkCmdBindIndexBuffer` calls, none repeated the bound buffer, offset and type (Waylith's own `frameStateCur` tracking already skips repeats; each mesh has its own index buffer). What remains is the plain number of draws and state changes per frame. Measured per frame on this laptop with the camera zoomed out (v13.66, 30-second window): about **820 draws, 500 descriptor-set binds, 700 index-buffer binds, 710 push-constant updates, 80 pipeline binds and 110 host-memory ranges** to synchronise; the translation layer spends 2.7 µs per draw, 2.7 µs per set bind and 1.1 µs per index bind on them (6.1 ms per frame in total), against about 1.6 ms at normal zoom. *Suggestion:* merging distant map sections into fewer, larger meshes at far zoom levels (or skipping small things below a size on screen) reduces all of these together and helps every slow CPU, native or translated; zoom-out is where players on this hardware feel lag (33–45 fps zoomed out against 60 fps zoomed in). A second, cheaper suggestion: every map section has its own index buffer, so nearly every draw changes the bound index buffer (about 495 switches per frame here, ~1.8 µs each in the D3D11 driver). Sub-allocating section index (and vertex) data from a few large buffers and selecting each section with `firstIndex`/`vertexOffset` removes those switches on every driver; bridge v13.74 now does this itself by copying the index buffers into one pooled buffer. **Measured (v13.74):** index-buffer switches dropped to about 25,000 in a whole 5-minute session, and the translation layer fell from 3.3 to 2.3 ms per frame.

**3.16 A new descriptor set for almost every draw (information, new).** The bridge skips re-binding a descriptor set that is identical to the one bound for the previous draw (same set object, same dynamic offsets, nothing changed in between). On the quicktest map this skip applied to **7,974 binds against 1,989,455 full binds** in one session: Waylith evidently binds a *different* `VkDescriptorSet` object for nearly every draw, even when it points at the same buffers and textures as the previous one. Native drivers handle this cheaply; translation layers (and drivers that validate or re-translate descriptors) cannot tell "new object, same contents" from a real change without comparing every binding, so every draw pays for a full descriptor update. *Suggestion:* where a draw's resources match the previous draw, re-use the same set object (a small cache keyed by the bound resources), or keep per-material sets alive across frames and change only the dynamic offset. This also reduces `vkUpdateDescriptorSets` work on native drivers. (Cause, from the 1.7 engine code: `VulkanMeshDrawEncoder.TryUploadUniforms` writes each draw's uniforms into a window of a per-frame uniform buffer and puts that window into a new descriptor set as a plain uniform buffer, so a new set is needed only because the offset changed. Binding the per-frame buffer once as a `UNIFORM_BUFFER_DYNAMIC` descriptor in a long-lived set and passing the window as a dynamic offset in `vkCmdBindDescriptorSets` would remove the per-draw set allocation and update on every driver. Bridge v13.75 now compares set contents itself, ignoring uniform offsets, to recover the skip.) **Measured (v13.75, 21 Oct):** the bridge now also copies every draw's uniform window into one ring buffer with a single upload per command buffer (about 1.09 million windows per session). Together with the content comparison, this took the translation layer from 2.3 to **1.2 ms per frame** and raised the 1% low from 9.2 to 21.5 fps. The dynamic-offset change suggested above would let any driver or layer get this saving without guessing.

**3.17 Command recording is now the largest part of the render thread's frame (information, new).** The bridge measures the wall time from `vkBeginCommandBuffer` to `vkEndCommandBuffer` of the frame command buffer: about **12 ms per frame** on this i5-5200U, against 3–6 ms for executing the recorded commands on D3D11. These 12 ms are the engine's render code walking the scene plus the bridge's own `vkCmd*` work; from bridge v13.64 on, the bridge's share is measured separately (an `rdtsc` pair per call) and the per-call device-status check it used to do was removed. Whatever the exact split turns out to be, on a 2-core CPU the frame is built mostly by the engine's recording code. *Suggestion:* for static map content (terrain, buildings, map-mesh sections that did not change), record once and re-use the command buffer or a secondary command buffer across frames, and spread recording of independent passes over worker threads. Either lowers frame time on every slow CPU, not only behind a translation layer. **Independent confirmation (21 Oct):** Fracture, a separate engine test (Bevy/wgpu, OpenGL and D3D11) on the same i5-5200U, measured the GPU busy for only 3–10 ms of a ~22 ms frame. On this class of laptop, CPU time per draw and per frame decides the frame rate, not shader cost.

### 3D. Robustness and start-up

**3.18 Silent render-thread death.** When the bridge failed `vkEndCommandBuffer`, the render thread stopped while the game kept running with music and a frozen frame; the only hint was in `Player.log`. *Suggestion:* treat a failed `vkEndCommandBuffer` or `vkQueueSubmit` like `VK_ERROR_DEVICE_LOST`: log the result code and pass name, exit with a message. Players report dialogs; they do not report freezes with music.

**3.19 Swapchain rebuild rate.** The per-frame size check is fine, but a wrong surface extent caused a rebuild every frame for a whole session without comment. *Suggestion:* one warning when rebuilds exceed N in M frames. **Observed (20 Oct):** on this 1920×1080 screen the game creates its swapchain at 1920×1080 and recreates it 4 s later at **1920×1177**, i.e. the window client area grows taller than the display. Harmless, but a client area larger than the monitor costs fill rate and on flip-model presentation prevents the compositor bypass. *Suggestion:* clamp the window to the monitor work area.

**3.20 GPU probe never completes on slow GPUs and reruns every boot.** `HardwareProfile.BeginProbe` runs `GpuProbe` on a job thread at startup. The smallest ALU dispatch is 65535 groups × 64 threads × 256 iterations (the calibration clamp) × 16 FLOP ≈ 17 GFLOP, about 70 ms on a ~250 GFLOP/s GPU (HD 5500). Calibration plus the sweep use up the 1500 ms budget, so `MeasureBandwidth` returns 0, the profile is "incomplete", is not stored, and the probe runs again on every boot (≈1.7 s of full GPU load plus a 256 MB and a 16 MB buffer during loading). In this build nothing reads the resulting tier. *Suggestion:* scale the group count down along with the iterations (or cap the dispatch time) so the probe fits the budget on slow GPUs, cache an "incomplete/low" result too, and skip the probe until a consumer needs the tier.

**3.21 Runtime SPIR-V 1.0 compilation on Vulkan 1.0 devices (new).** On a 1.0 device the log says "shaders will be compiled for spirv_1_0 and baked shader packs will not be used", so every start compiles the full shader set at run time, which is a noticeable part of the boot time on a 2-core laptop (the bridge then caches its own HLSL translation on disk: 41 of 41 shaders were cache hits on later starts). *Suggestion:* also ship a baked pack targeting SPIR-V 1.0 (Slang can emit `spirv_1_0`), so old devices get the same fast start as new ones.

**3.22 Shader modules created after the map is on screen (new).** The bridge logs each shader module creation. Several modules (and their pipelines) are created only after the first frames of the colony map have been presented, i.e. the first time a new kind of object or effect is drawn. Each costs the SPIR-V compile/translation plus the driver's own compile of the final GPU code in that frame, which shows up as a hitch exactly when something new appears on screen (first raid, first fire, first weather change). The bridge now creates the shader objects of earlier runs in a background thread at start-up (v13.64), which hides the driver part but not the translation. *Suggestion:* create all pipelines that the game can use during loading (or in a background thread with a `VkPipelineCache` that is saved to disk), as DXVK and most engines recommend; on slow hardware a slightly longer loading screen is much better than hitches during play.

**3.23 Native libraries inherit the user's number format.** In the 1.7 process, C runtime `printf` in native libraries prints a decimal comma on a Dutch Windows (the bridge's own logs and CSV files were affected until it switched to the C locale explicitly). Anything native that formats or parses floats (shader compilers, loaders, file writers, config parsers) can break on comma locales. The managed side already runs invariant-culture saves via the launcher option the bridge uses; for native code the safe default is `setlocale(LC_NUMERIC, "C")` at start-up. Related, from #bug-reports (18 Oct): 1.7 builds up to at least 1.7.4982 wrote saves with the system decimal separator and read them back with a dot. On Dutch, German and French Windows, pawns aged centuries and need bars overflowed. The bridge's launcher starts the game in .NET invariant-globalization mode as a workaround. If this has been fixed since, please disregard.

### 3E. Simulation speed and frame pacing

**3.24 Tick rate is capped by frame rate at higher speeds.** `TickManager.TickManagerUpdate` (1.7) simulates until real time is caught up, but stops after **2 × `TickRateMultiplier` ticks** or after **45.45 ms of ticking** (`WorstAllowedFPS = 22`), whichever comes first, and then drops the remaining time. At speed 3 the target is 360 ticks/s, so below ~30 fps the simulation cannot reach the chosen speed however fast the CPU simulates. On weak GPUs/iGPUs the game speed then silently drops. *Suggestion:* allow more ticks per frame when the frame rate is low (time-budgeted, e.g. up to 8-10 ms of simulation per frame), or show the achieved speed in the time controls. The bridge now measures achieved vs. target ticks per second with a read-only diagnostic mod. **Measured:** at Normal speed the game holds 93–98% of 60 ticks/s; at Ultrafast 85–100% of 900 ticks/s depending on the scene.

**3.25 Frame pacing on this hardware.** Measured while playing, quicktest map, Normal speed, bridge v13.60–v13.61 (20 Oct): **52–58 fps average, 1% low 15–21 fps, 99% of frames under 26–29 ms**, consistency 87–89%; the game reaches its 60 fps limit most of the time on lighter maps. The GPU is never the limit (it has always finished the previous frame); the translation layer costs about **10 µs per draw** (3–5 ms per frame). Split of a frame on the engine side (counter mod, frame order of `Game.UpdatePlay`): simulation ticks **1.1 ms**, world + map update and drawing **1.6 ms**, the rest (UI, render submission, present, waiting for the frame limit) ~16 ms. **Frames over 50 ms:** at Normal speed 23–30 per 4-minute run, almost all on the engine side ("rest" part, no GC, 1–2 ticks). At Ultrafast 93% of them contain many simulation ticks (~29 ticks in one 136 ms frame on a 2-core Broadwell i5); since the loop stops after 45 ms of ticking, the overrun beyond 45 ms points at single heavy ticks (rare/long ticks) or other per-frame work. **.NET GC is not the cause:** workstation GC, 0.3–0.7% of the time in 4–10 ms pauses, 1–2 full collections per run. *Suggestions:* (1) an option (or automatic choice on slow CPUs) to lower the 45 ms tick budget — the community mod "FPS Stabilizer" does exactly this for 1.4–1.7 by raising the 22-fps floor to 60; (2) spread the work of rare/long ticks over several ticks; (3) a frame-time / 1%-low readout in the developer Frame Profiler would make performance reports from players far more precise.

### 3F. Assets

**3.26 Low-resolution plant textures without mips.** Players on this setup noticed soft agave and saguaro cacti. In `Assets.zip`, `Things/Plant/Agave/AgaveA.psd.dds`, `AgaveB` and `SaguaroCactus.psd.dds` (and 445 of 2693 thing textures in total) are 64×64 BC7 with a single mip level, while these plants are drawn about 2 cells (≈130 px at normal zoom) wide: magnified ~2× when zoomed in, and without mips they alias when zoomed out. If the bake downsized them, a higher source resolution plus a mip chain would restore the crisp outlines.

**3.32 BC7 atlas copies via 1:1 `vkCmdBlitImage` (new, 21 Oct).** A community fix, RimWorldAMDFix (MIT, github.com/RevenantBob/RimWorldAMDFix), shows that on AMD driver 26.10.1 (RX 9070 XT, 1.7.4984) the 1:1 blit of BC7-compressed item sprites into the RGBA8 atlas copies only 4 of 64 texels per block, so items draw as only their top-left corner. The fix is a Vulkan layer that redoes that one copy. Translation layers hit the same call (3.1, 3.2). *Suggestion:* build atlases with a sampled draw, or with `vkCmdCopyImage` plus a decode pass, instead of a format-converting blit. That would fix this AMD driver bug and the translation-layer case together.

### 3G. Added 21 October: player messages, residency, layers, heaps, heat

**3.27 Tell players which "no Vulkan" case they are in (new).** The launch failure says "The graphics driver could not start Vulkan" for every case in 2.1. The cases have different fixes: no Vulkan driver exists for this GPU, a driver exists but is too old (OEM driver), or no GPU driver is installed at all ("Microsoft Basic Display Adapter"). *Suggestion:* before showing the dialog, check two things. Does any Vulkan ICD exist for the adapter (`HKLM\SOFTWARE\Khronos\Vulkan\Drivers`, or the adapter's `VulkanDriverName` value)? And what are the adapter name and driver date (`Win32_VideoController`)? Then add one line of advice: "your GPU has no Vulkan driver (pre-2015 Intel, GeForce 400/500, Radeon HD 5000/6000)", "update the graphics driver from the GPU maker, not only the PC maker", or "no graphics driver installed". The bridge's menu does this check; its name patterns are in `Gpu-Compat.ps1` (MIT) if useful.

**3.28 Textures sampled before their first upload (new; validation log from 1.7.4979, GTX 1080 Ti).** That thread's `RimWorld_VulkanValidation.txt` contains a single error type: `VUID-vkCmdDraw-None-09600`, 218 occurrences. Draws in `MapRenderFeature.MapMainPass` and in the pawn-cache render sample five images whose layout is still `UNDEFINED`, across complete 10-level mip chains. This looks like the lazy-residency path: the descriptor is written before the upload and transition have been recorded. On strict drivers the draw reads garbage, which matches the red/green/magenta shapes reported on effects. D3D11 has no layouts, so translation layers don't show it. *Suggestion:* bind a placeholder texture until the upload has been recorded, or record the upload and barrier before the first draw that samples the image.

**3.29 Implicit Vulkan layers at the early fallback stages (new).** Several threads report VRAM climbing to 100% at the main menu until Discord is closed. Discord installs an implicit Vulkan layer, and the logs also show OBS, RTSS, EOS, Rockstar and GOG Galaxy layers. Implicit layers are disabled only at fallback stage 3. *Suggestion:* list the active implicit layers in `Player.log` at start-up, so these reports can be recognised at once. Consider also starting with `VK_LOADER_LAYERS_DISABLE=~implicit~` unless the player opts in. The bridge's launcher does this for its own runs.

**3.30 Only memory heap 0 is used (new, from logs).** On a Surface Laptop 4 (two 256 MiB device-local heaps) the log shows allocations only from heap 0. Render targets alone (263 MiB) exceeded that heap, and `ErrorOutOfDeviceMemory` followed during a re-upload in `Texture2D.EnsureResident`. The same log has 4,078 VMA blocks for 275 MiB, so almost every allocation is a dedicated block. *Suggestion:* let VMA choose among all heaps of the wanted type, and raise the dedicated-allocation threshold on small heaps.

**3.31 Laptop heat (information, new).** On the test laptop, sustained 60 fps raised the temperature until the CPU throttled to about 20% of its clock, giving multi-second stutters. Capping at 45 fps (done by the bridge) and setting Windows' maximum processor state to 99% (disables Turbo) removed the throttling in the measured run. The machine had also had its power state reset by unplugging and replugging the charger, so the two effects are not yet separated. *Suggestion:* a frame-rate cap option below 60 (30/45) in the graphics settings, if not already planned, gives thin laptops a steadier game than an uncapped 60.

Thank you for building an engine that accepts a Vulkan 1.0 device at all; it made this work possible.
